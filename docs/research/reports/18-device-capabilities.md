# Verdict

Treat both phones as **capture, playback, and upload clients for a cloud analysis engine**. They can perform useful preparation on-device, but neither has a verified third-party camera profile or a documented LiteRT NPU path for its Exynos chip. One-off GPU benchmarks show the S23 FE ahead of the A55, but they do not establish sustained match-analysis performance.

The chipsets are as expected: the **Indian Galaxy S23 FE (SM-S711B) uses Exynos 2200**, not the Galaxy S23’s chipset; the **Galaxy A55 (SM-A556E) uses Exynos 1480**. Samsung’s India specs confirm the S23 FE’s Exynos 2200 and 8 GB RAM; Samsung identifies the Xclipse 920 GPU and NPU in the Exynos 2200, and the Xclipse 530 GPU and NPU in the Exynos 1480. ([Samsung India S23 FE specs](https://www.samsung.com/in/support/mobile-devices/specifications-for-the-new-galaxy-s23-fe/), [Exynos 2200](https://semiconductor.samsung.com/processor/mobile-processor/exynos-2200/), [Exynos 1480](https://semiconductor.samsung.com/processor/mobile-processor/exynos-1480/))

**The exact CameraX/Camera2 modes on your two physical handsets remain UNVERIFIED.** Samsung’s stock camera modes do not guarantee that a third-party app can request the same resolution, frame rate, stabilization, or encoder settings.

## Camera API facts to verify on the handsets

CameraX **1.6.2** is the current stable release checked on October 10, 2026. It has a stable high-speed video session API, but what it can use depends on the phone’s camera implementation. ([CameraX release notes](https://developer.android.com/jetpack/androidx/releases/camera))

Probe every rear camera ID on both devices for:

- `INFO_SUPPORTED_HARDWARE_LEVEL`, `REQUEST_AVAILABLE_CAPABILITIES`, including `MANUAL_SENSOR`, `RAW`, and `CONSTRAINED_HIGH_SPEED_VIDEO`.
- `SCALER_STREAM_CONFIGURATION_MAP`, supported high-speed sizes and frame-rate ranges, and normal video size/rate combinations.
- Available video-stabilization modes.
- `MediaCodecList` encoder/decoder profiles and `VideoCapabilities` size/rate support.

Android documents these camera and codec queries in its [Camera2 characteristics](https://developer.android.com/reference/android/hardware/camera2/CameraCharacteristics), [high-speed stream map](https://developer.android.com/reference/android/hardware/camera2/params/StreamConfigurationMap), and [video codec capability APIs](https://developer.android.com/reference/android/media/MediaCodecInfo.VideoCapabilities). **The saved slow-motion file’s playback frame rate and timebase are also UNVERIFIED.** Inspect an actual clip from each phone before building analysis around slow-motion timing.

## On-device preprocessing and cloud split

| On the phones | In the cloud |
|---|---|
| Capture and save the original video; show an immediate local preview and thumbnails; preserve orientation and timestamps; detect file errors; queue and resume uploads. | Decode the original; run player, court, racket, ball, and event analysis; estimate trajectory and speed; segment rallies; calculate stats and recommendations; maintain match history and comparisons. |
| Calculate a simple audio energy/onset track. This is a **low-cost implementation estimate**, not a handset benchmark. | Resolve uncertain detections and present evidence-linked results. |
| Optionally generate a smaller upload proxy with hardware encoding **after querying supported codecs**. Keep the original so processing can be retried. | Produce any expensive crop, tracking, or model passes from the original. |
| Optionally run a sparse person detector to create a visual hint or preview overlay. Do not make its detections canonical. | Keep all score, identity, and coaching claims tied to confidence and video evidence. |

A concrete optional detector is Google’s pretrained **EfficientDet-Lite0 INT8**, model file `lite-model_efficientdet_lite0_detection_metadata_1.tflite`, about **4.4 MB**, input **320×320**. Google reports **37 ms** on Pixel 4 with four CPU threads and **25.69% COCO 2017 mAP**; that is a published reference, not a measurement on either Galaxy. The model is COCO-trained, not racket-sport-trained, so use it for sparse person boxes, not ball/shuttle tracking or player identity. The model is listed as Apache-2.0 in the [LiteRT Community model repository](https://huggingface.co/litert-community/efficientdet); the performance and size figures are from Google’s [Model Maker object detection guide](https://developers.google.com/edge/litert/libraries/modify/object_detection).

For current inference dependencies, Google’s October release is **LiteRT 2.3.0**. Its Android GPU package is distributed separately; GPU execution uses OpenCL/OpenGL, but model compatibility and speed on these Xclipse drivers remain **UNVERIFIED**. ([LiteRT 2.3.0 release](https://developers.google.com/edge/litert/releases/litert_oct), [GPU documentation](https://developers.google.com/edge/litert/next/gpu)) Android NNAPI has been deprecated since Android 15, so do not make it a required path for these Android 16 phones. Samsung’s Neural SDK is no longer provided to third-party developers; Samsung ONE is open source, but its existence does not verify app-accessible NPU support on these two chips. ([Android NNAPI migration guide](https://developer.android.com/ndk/guides/neuralnetworks/migration-guide), [Samsung Neural SDK notice](https://developer.samsung.com/neural/overview.html), [Samsung ONE](https://github.com/Samsung/ONE))

## Recommended capture profiles

| Phone | In-app recorder profile |
|---|---|
| **S23 FE** | Start with rear main camera, landscape, fixed wide framing, **1080p60 AVC/H.264 with AAC** if the runtime probe confirms it. Offer 4K30 as a detail option. Do not default to 8K24 or slow motion. |
| **A55** | Use the same 1080p60 AVC/H.264 baseline if the probe confirms it; fall back to 1080p30. Offer 4K30 when more spatial detail matters. Do not offer 4K60 or 240 fps as app features unless Camera2 proves the mode and you test the saved file. |

These are **recommended targets, not verified CameraX profiles**. For both phones, favour a static tripod or stable support, full play area, good light, and no digital zoom. That follows your team’s own M4 testing, where static footage worked much better for ball tracking than handheld badminton footage. If manual sensor control is exposed and lighting allows, test a 1/120 s shutter at 60 fps; otherwise use auto exposure. If video stabilization can be disabled, test it on a tripod because electronic cropping may change the court framing.

## Recommendation

Build cloud match analysis. Make the phone experience feel fast with local preview, clear upload stages, resumable transfer, and results that appear progressively. Keep on-device processing to file handling and optional sparse helper detections. The current evidence does not justify promising full offline analysis on either handset.

## 3 Biggest Risks

1. **Camera API mismatch:** the stock camera’s modes may not be available to your app, especially high-speed capture and stabilization controls.
2. **Footage quality:** a handheld informal clip may demonstrate upload and UI polish but is weak evidence for court geometry, ball tracking, or officiating.
3. **Heat and transfer time:** the benchmark and thermal results are not capture-pipeline tests, and venue Wi-Fi/5G upload speed is unknown.
